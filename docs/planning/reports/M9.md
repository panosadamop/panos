# M9 report — Multi-PC control plane and web dashboard

- **Date:** 2026-10-12
- **Status:** complete except for the owner's live check with a second real PC; awaiting owner approval. **Not committed** (M8 was committed as `9442fa8`).
- **Exit criterion:** see and use Panos across your PCs, monitor jobs and approvals in a web dashboard. **Met on this PC:**
  - a real hub plus a real node in separate processes;
  - TLS on loopback;
  - passkey sign-in in real Chromium.

  **Not yet verified:** two physical PCs (Windows + macOS/Linux) on the LAN. That needs the owner (`docs/planning/multi-pc-setup.md`).

## What you can do now

```text
Hub PC:   panos hub init | serve | status | enroll-code | passkey-code | nodes | revoke <pc> | dispatch <pc> "…" | export-ca
Any PC:   panos node join <hub-url> --code … --fingerprint … | status | leave      (or desktop Settings → Hub)
Browser:  https://<hub>:48700 → passkey → PCs (add/revoke), jobs (live steps, pause/resume/cancel),
          approvals (exact action, approve/reject), send a job (target shown first), AI usage,
          traceability, hub log (hash chain, verify) · Greek/English
```

## Defects found and fixed during M9 verification

1. The inventory was sent only at connect, so a project registered afterwards never reached the hub. It is now republished on change (found by the real-node test).
2. The CLI crashed printing "→" on redirected cp1252 output (found by the real-process test). It now replaces characters it cannot encode.
3. The real-process test "hung" for 90 s: the harness left `stderr=PIPE` unread and the hub blocked on logging. Logs now go to files.
4. Coverage under-reported code that runs in SQLAlchemy's greenlets (`nodes.py` showed 66% although every enrollment runs it). Coverage now traces greenlets.
5. Test design: a synchronous TestClient called from the hub's event loop deadlocks; such calls now run in a worker thread.

## Known limitations

1. Verified on one PC only (loopback); real LAN, firewall and macOS/Linux behaviour are the owner's check.
2. The dashboard polls (5 s) instead of receiving pushes.
3. There is no hub background service or installer option; the hub in the frozen sidecar is untested.
4. A compromised hub could dispatch jobs and approve actions under each PC's policy (accepted residual risk R-17; a PC can refuse hub decisions).
5. The dashboard needs the hub CA trusted in each browser and a LAN host name (WebAuthn does not accept IP addresses).
6. Earlier open items still apply: the R-15 search provider decision, ADR-026/027 acceptance, and the M8 live account checks.
