# Claude Code Instructions — Panos

You are implementing **Panos**, a production-quality local-first AI desktop assistant. Read `README.md` and all linked specification documents in `docs/specs/` before making architectural decisions. Accepted ADRs in `docs/adr/` are binding; the approved plan is `docs/planning/PLAN_PROPOSAL.md`.

## Working principles

1. Implement in small, testable vertical slices.
2. Do not bypass the policy/permission/tool layers.
3. Never give model providers direct arbitrary shell, filesystem, browser or desktop access.
4. Preserve cross-platform boundaries. OS-specific behavior belongs behind adapters.
5. Local-only projects must never leak protected source code, documents, prompts, screenshots or derived sensitive context to cloud providers.
6. Every consequential action must be auditable.
7. Every long-running task must support cancellation; important workflows should support pause/resume and checkpoints.
8. Prefer native APIs/CLIs over mouse/keyboard automation. UI automation is a fallback.
9. All external integrations must be replaceable through interfaces/adapters.
10. Do not silently expand permissions.

## Development workflow

For each implementation unit:

- identify requirement IDs being implemented (registry: `docs/traceability/requirements.yaml`);
- tag tests with requirement IDs (`@pytest.mark.req("FR-011")`, or `[FR-011]` in Vitest test names);
- create/update tests first or alongside implementation;
- implement;
- run format/lint/type-check/tests;
- report changed files and requirement coverage;
- do not commit unless the user approves;
- keep `project-log.md` (conversation/decision log) and `considerations.md` (risks, trade-offs, deviations, follow-ups) up to date;
- stop at each milestone exit with a report in `docs/planning/reports/` and wait for approval.

## Architecture constraints

Use a modular monorepo. Python owns orchestration, agents, policies, tool execution, knowledge and voice services. React/TypeScript owns desktop/web presentation. Tauri provides the desktop shell. Communication between UI and local runtime uses a versioned local API/WebSocket contract.

Do not hard-code AI vendors, IDEs, operating systems, Git providers, knowledge providers, STT/TTS engines or project technology stacks.

## Project-generation behavior

Panos itself uses the architecture above. Applications generated by Panos may use any requested technology. First-class generation knowledge must include:

- Python / FastAPI / Django
- Java / Spring Boot / Vaadin
- React / TypeScript
- Node.js / NestJS
- PHP / Laravel
- PostgreSQL / MongoDB
- Docker / Kubernetes
- GCP / Azure / AWS

When a user explicitly requests a stack, honor it. Otherwise propose a stack and require approval before project scaffolding.

## Definition of done

A feature is not complete until applicable automated tests pass, errors are handled, security/privacy rules are enforced, audit events exist for consequential behavior, and relevant requirements can be traced to implementation/tests.
